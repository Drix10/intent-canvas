# Human Code Writing Standard (How Code MUST Be Written)

To maximize **Technical Implementation & Technical Understanding (20/20)** and **Functionality (25/25)**, code generated by AI MUST follow human senior engineering standards:

### 🧘 0. Lazy Senior Dev Mode (The Ponytail Principle)
*Lazy means hyper-efficient, not careless. The best code is code that never needed to be written.*

Before writing any code, climb the **7-Rung Efficiency Ladder**:
1. **YAGNI**: Does this feature actually need to be built at all?
2. **Reuse**: Does a helper, utility, or pattern already exist in this codebase? Reuse it—never rewrite.
3. **Stdlib**: Does the language standard library already solve this? Use native methods.
4. **Platform**: Does a native browser or Node.js platform feature cover it? Use it.
5. **Installed Libs**: Does an already-installed dependency solve it? Use it.
6. **One-Liner**: Can this logic be expressed cleanly in one line? Make it one line.
7. **Minimum Code**: Only then write the smallest, cleanest code that solves the problem.

**Rules of Lazy Senior Engineering**:
- **Deletion Over Addition**: Prefer fewer lines, fewer files, and boring simple code over clever over-engineering. The shortest working diff wins.
- **Root-Cause Fixes Over Symptom Patching**: Fix bugs at the shared root function once instead of wrapping callers in individual band-aids. Grep all callers before editing.
- **Mark Deliberate Ceilings**: When taking a simple shortcut for speed (e.g. in-memory map, naive scan), mark it with a `ponytail:` comment describing the ceiling and upgrade path:
  `// ponytail: in-memory cache ceiling ~10k items; upgrade to Redis for multi-instance horizontal scaling`
- **What We Are NOT Lazy About**: Understanding the problem fully before coding, strict input validation at trust boundaries, security, error handling, accessibility, and real-world hardware/platform calibration. Non-trivial logic must leave behind ONE smallest runnable assertion/check.

### 1. Domain-Driven Naming & Expressiveness
- **Variables & Functions**: Use explicit domain terminology (`telemetryPayload`, `userSessionToken`, `orderFulfillmentQueue`) instead of vague AI defaults (`data`, `res1`, `item`, `val`, `temp`).
- **Function Names**: Action-oriented and descriptive (`calculateUsageQuota`, `validateAuthHeader`, `ingestLogStream`).

### 2. Clean Architecture & Modular Separation
- **Backend**: Strict 3-tier layering: `Route Handler` ➔ `Middleware/Validator` ➔ `Service Layer (Business Logic)` ➔ `Mongoose Model`.
- **Frontend**: Pages orchestrate features; custom hooks manage state (`useTelemetryStream`, `useAuth`); UI components render view logic.
- **Single Responsibility**: No monolithic files over 200 lines. Break UI and services into focused modules.

### 3. Fail-Fast & Centralized Error Handling
- Never wrap whole functions in empty try-catch blocks.
- Use explicit Custom Errors (`AppError`, `UnauthorizedError`, `ValidationError`) handled by centralized Express error middleware.
- Return structured API responses:
  ```json
  {
    "success": false,
    "error": {
      "code": "INVALID_PAYLOAD",
      "message": "Field 'email' must be a valid email address"
    }
  }
  ```

### 4. Strict Type Safety
- Interfaces over `any`: Define strict TypeScript interfaces for all API payloads, component props, and database documents.
- Zero `@ts-ignore` or `as any` escape hatches.

# Anti-AI Code & Anti-AI Comment Rules (How NOT to Write Code)

Code generated with AI often leaves distinct "AI slop" signatures that ruin code quality ratings. Follow these anti-AI code rules strictly:

### 🚫 Rule 1: Zero AI Comment Noise
AI loves inserting lazy, redundant comments that state the obvious. **Delete all AI comment fluff!**

- ❌ **BAN THIS (AI Comment Slop)**:
  ```typescript
  // Import React and hooks
  import React, { useState, useEffect } from 'react';
  
  // Helper function to format date
  const formatDate = (date) => { ... }
  
  // Render the component
  return (
    <div>...</div> // Return div
  );
  ```

- ✅ **DO THIS (Clean Human Standard)**:
  ```typescript
  import React, { useState, useEffect } from 'react';

  export const formatDate = (dateString: string): string => { ... };
  ```
  > *Rule of thumb*: Code should be self-documenting. Comments are ONLY allowed for complex math formulas, security edge cases, or non-obvious business logic.

---

### 🚫 Rule 2: BAN Silent Fallback & Error Swallowing
AI often writes code that swallows errors silently to avoid crashing, making debugging and judging review a nightmare.

- ❌ **BAN THIS**:
  ```typescript
  try {
    const data = await fetchApi();
    return data;
  } catch (error) {
    // Return empty array on error
    return [];
  }
  ```

- ✅ **DO THIS**:
  ```typescript
  try {
    return await fetchApi();
  } catch (error) {
    logger.error('Failed to fetch API telemetry', { error });
    throw new ApiFetchError('Telemetry stream unreachable', { cause: error });
  }
  ```

---

### 🚫 Rule 3: BAN Redundant Utilities & Boilerplate
- ❌ **No duplicate helpers**: Never create `formatDate` or `cn` helper functions in 5 different files. Consolidate into `utils/`.
- ❌ **No inline SVG dumps**: Never dump 50-line inline SVG paths directly inside page components. Import clean icons from `lucide-react`.
- ❌ **No generic commit messages**: Never commit with `fixed bug`, `update code`, or `asdf`. Use conventional semantic commits (`feat: implement JWT auth middleware`).

# Anti-AI Documentation & Prose Rules (Human Writing Standard)

To ensure READMEs, technical documentation, and project descriptions score full points in **Documentation (10/10)** without sounding AI-generated, strictly enforce these writing rules:

### 🚫 1. Banned AI Buzzwords & Fluff Terms
Replace these machine-generated buzzwords on sight with direct, concrete human phrasing:

| AI Buzzwords (NEVER USE ❌) | Human Alternatives (USE ✅) |
| :--- | :--- |
| `delve into`, `deep dive`, `unpack` | explore, examine, break down |
| `tapestry`, `landscape`, `realm`, `ecosystem` | system, architecture, field, domain |
| `robust`, `seamless`, `comprehensive`, `cutting-edge` | reliable, smooth, complete, modern |
| `game-changer`, `paradigm-shift`, `revolutionary` | state specific technical improvement |
| `leverage`, `utilize`, `harness`, `foster` | use, enable, build |
| `testament to`, `underscores`, `pivotal` | shows, proves, key |
| `at its core`, `synergy`, `interplay` | state the core architecture directly |
| `it's worth noting that`, `in order to` | (cut completely or replace with "to") |

### 🚫 2. Formatting & Structural Anti-Tells
- **No Chatbot Artifacts**: Strip all conversational AI tics (`I hope this helps!`, `Certainly!`, `Here is your code...`, `Let's dive in!`, `In today's fast-paced world...`).
- **No Generic Closers**: Ban fluff conclusions (`The future looks bright`, `Only time will tell`, `As we move forward`). End with concrete technical specifications or next steps.
- **No Copula Avoidance**: Use direct verbs (`is`, `has`) instead of press-release verbs (`serves as`, `boasts`, `features`, `presents`).
- **No Unfilled Placeholders**: Ban `[INSERT LINK HERE]`, `[Your Name]`, `2026-XX-XX`, `<!-- TODO -->`.
- **Clean Typography**: Restrain bold overuse (max 1 bold phrase per major section) and avoid emojis in technical headers.

# Checkpoint Tracking & Task Completion Protocol (Context Continuity)

To ensure we **never lose track of progress, forget context, or get off plan**—even when changing AI chats, switching models, or performing developer handoffs—all development MUST follow this strict checkpoint protocol:

### 📍 1. Checkpoint Breakdown Standard
Before starting any implementation phase, break down the work into numbered, verifiable checkpoints:
- `[ ] Checkpoint 1: Database Schemas & Zod Validation Middleware`
- `[ ] Checkpoint 2: Core Auth & JWT Session Service`
- `[ ] Checkpoint 3: Spatial Canvas Layout & Lenis Scroll Integration`
- `[ ] Checkpoint 4: Real-time Telemetry & WOW Feature Implementation`

### 📝 2. Instant Task Completion Logging
Immediately upon completing each checkpoint, mark it as completed `[x]` and log a clear summary of work and changes made:
```markdown
### ✅ [COMPLETED] Checkpoint X: [Task Name]
- **Timestamp / Time Elapsed**: [e.g. 1:30 - Phase 5]
- **Files Created / Modified**:
  - `server/src/models/Telemetry.ts` [NEW]
  - `client/src/components/SpatialCanvas.tsx` [MODIFY]
- **Summary of Work Done**: Brief, technical description of changes, parameters, and algorithms implemented.
- **Verification Result**: Verified with zero console errors / build compilation clean.
- **Next Checkpoint**: Checkpoint X+1: [Next Task Name]
```

### 🔄 3. Persistent Context via `CHECKPOINTS.md`
- Maintain a single persistent `CHECKPOINTS.md` file in the project root.
- When switching AI chats or sessions, the new session MUST first read `CHECKPOINTS.md` to resume execution seamlessly from the exact active checkpoint without re-inventing, duplicating, or skipping steps.
